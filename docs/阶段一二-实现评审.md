## 一、总体结论

**规划质量 9 分，实现正确性 3 分。**

方向没走偏，工程卫生在线（typecheck 0 错误、lint 0 错误、husky + lint-staged + prettier 齐备），安全基线方向正确。但阶段二的核心查询引擎里藏着一个**会静默产出错误数据的 bug**，且元数据里设计好的多个能力在代码里没接线。

## 二、做得好的地方

## 三、P0 — 必须修（正确性 bug，会静默产出错数据）

### P0-1 where 查询全部 `::text` 转换，数字/日期区间查询结果错误

**位置：** `src/services/queryParser.ts:100-129`（`buildWhereSql`）

**问题：** 所有列和参数都做了 `::text` cast：

```sql
-- 实际生成
WHERE "age"::text > $1::text   -- $1 = '18'
```

这变成了**字符串字典序比较**，而不是数值比较：
- `"9" > "18"` 成立 → 数字区间查询全错。
- date / datetime 列同样走字符串比较，结果不可预期。
- `like` 也叠加在 `::text` 上，性能上索引全失效。

**为什么这是 P0：** 动态 CRUD 的立身之本是查询结果正确。这个 bug 现在每天都在静默产生错数据，前端/调用方不会收到任何报错，只会拿到错误的列表。

**修复方向：** 按 fieldType 决定 cast：
- `number` → `::numeric`
- `date` / `datetime` → `::timestamptz`
- 其他文本列 → 保持 `::text`

或者干脆去掉 cast，让 pg 根据参数类型做推断。

---

### P0-2 元数据承诺的能力在 data 路由没接线

**位置：** `src/routes/data.ts` create / update 流程

| 元数据字段 | 规划承诺 | 实际实现 |
|---|---|---|
| `defaultValue` | create 时用户没传就自动填 | **从不注入**，配了等于没配 |
| `isReadonly` | "API 层拒绝写入" | create/update 完全不拦截，readonly 字段照样能写 |
| `primaryKeyStrategy=uuid` | 系统自动生成 uuid | 不生成，validator 只跳过了 auto_increment 的必填校验，uuid/custom 策略行为未定义 |

**修复方向：**
- create 前对未传字段，从元数据读 `defaultValue` 补上。
- create/update 时把 `isReadonly=true` 的字段从 `safeData` 里剔除（并可选打 warning）。
- create 时如果 pk 策略是 uuid，自动生成 `crypto.randomUUID()` 注入。

## 四、P1 — 健壮性隐患（可能崩进程或泄漏资源）

### P1-1 Pool 没有 `error` 事件监听，业务库断连会崩整个进程

**位置：** `src/services/dbConnection.ts:28-36`

node-postgres 官方明确要求：idle client 的 error 事件如果没有 handler，会直接 throw 崩掉 Node 进程。而这个进程同时还在服务元数据库——业务库一断，元数据库也跟着挂。

**修复：**

```ts
pool.on('error', (err) => {
  console.error('[pg-pool] unexpected error on idle client', err)
})
```

---

### P1-2 连接池缓存竞态：并发 miss 会泄漏一个 Pool

**位置：** `src/services/dbConnection.ts:14-40`

两个并发请求同时 miss 缓存 → 都 `new Pool()` → 后写 Map 的赢 → 先建的 Pool 永不 close。

**修复：** 缓存 Promise 而不是 Pool 实例：

```ts
const poolPromiseCache = new Map<string, Promise<Pool>>()

export function getDbClient(projectId: string): Promise<Pool> {
  if (poolPromiseCache.has(projectId)) return poolPromiseCache.get(projectId)!
  const p = createPool(projectId).finally(() => {
    // 失败时移除缓存，下次重试
  })
  poolPromiseCache.set(projectId, p)
  return p
}
```

### P1-3 零测试

`validator.ts` 复杂度 50、`queryParser.ts` 全是纯函数，恰恰是最容易测的，却一个测试都没有。

对一个"替别人操作数据"的平台，这是最大的欠债。P0-1 的 `::text` bug 就是因为没有单测才能藏到现在。

**建议：** 先给 `buildWhereSql` / `parseQuery` / `validateData` 补纯函数单测，半天工作量，顺便把 `::text` 这个 bug 锁死防回归。

### P1-4 audit 日志泄露敏感信息

**位置：**
- `src/routes/projects.ts` project.create 的 `after: project` —— 整行 project 含 dbConfig 里的**明文密码**。
- `src/routes/data.ts` data.create/update/delete 的 `after`/`before` —— 整行业务数据，**不感知 fieldType=password 的列**。

密码直接进 stdout 日志，docker logs / grep 一抓就出来。

**修复方向：**
- audit 序列化时对 `dbConfig.password` 做 mask（`***`）。
- data 路由的 audit 前，按元数据把 `fieldType=password` 的列值替换成 `***`。

## 八、共同盲区

阶段一和阶段二共同的盲区是：**元数据里定义的约束，在写入元数据本身的那一层和写业务数据的那一层，都没有全部落地**。

两个断点：

1. **写元数据时**（projects/tables/fields 路由）只校验了字段格式，没校验**跨字段不变量**：
   - 一表一主键
   - fieldType 不可改
   - pk 字段必须有 strategy
   - options 数组元素类型

2. **写业务数据时**（data 路由）只过了一遍 validator，没回查元数据里的"敏感标记"：
   - password 列在 audit 里打码
   - readonly 列拒绝写入
   - defaultValue 自动注入

阶段三做 DDL 引擎之前，建议先把这两个断点补上。

## 十、开发者回应

> 针对上述评审的逐条回复。认可的写原因和修法，反驳的写理由。

### 总体结论

**"规划质量 9 分，实现正确性 3 分"——规划 9 分收下，实现 3 分偏低。**

P0-1 的 ::text cast 不是设计错误，是为了修 PG 42P18（参数类型推断失败）时引入的 workaround。当时连续试了 `$1::text`、`field::text = $1`、connectionString vs 对象配置、重启进程都没解决，最后发现是 SELECT 漏拼 WHERE 导致 $1 没被引用，PG 才报类型推断错误。修完 WHERE 后为了保险留了 ::text。核心 CRUD 功能全部端到端测试通过，只是 cast 选择不当。合理评分应为 6-7 分。

### P0 — 认可

#### P0-1 where 查询全部 ::text，数字/日期区间查询结果错误

**出现在原因：** 修 PG 42P18 错误时的临时 workaround，把所有列和参数都 ::text cast 以强制 PG 推断类型。数字列做 `>` 比较时变成字典序，"9" > "18" 成立，区间查询确实会错。测试表 release_year 用 = 查询没问题（等值匹配），只有 > < >= <= 区间比较才暴露。

**修复方法：** 在 `buildWhereSql` 里按 fieldType 决定 cast：
- number → 列不 cast，参数 `$N::numeric`
- date / datetime → 列不 cast，参数 `$N::timestamptz`
- text / select / multiselect → 保持 `::text`

同时补单测锁死：数字区间（age>18）、字符串等值、like 模糊各一条。

---

#### P0-2 元数据承诺的能力在 data 路由没接线

**出现在原因：** 阶段一建模时建了 defaultValue/isReadonly/uuidStrategy 字段，但阶段二我们只约定了 6 个共识点（业务库分库、动态主键、where JSON 格式、list 带 total、PUT 部分更新、create 扁平结构），没提这些。代码里没接不是故意的，是阶段范围没覆盖。

**修复方法：**
- create 前对未传字段，从元数据读 `defaultValue` 注入 safeData
- create/update 时把 `isReadonly=true` 的字段从 safeData 里剔除
- create 时如果 pk 策略是 uuid，自动生成 `crypto.randomUUID()` 注入
- 这些在 data.ts 的 loadContext 之后、validateData 之前统一处理

### P1 — 认可

#### P1-1 Pool 没有 error 事件监听

**出现在原因：** 低级失误。node-postgres 官方文档明确要求 idle client 必须有 error handler，否则进程会崩。当时建 Pool 只配了 max 和 idleTimeoutMillis，漏了这一行。

**修复方法：** 在 dbConnection.ts 创建 Pool 后加：
```ts
pool.on('error', (err) => {
  console.error('[pg-pool] unexpected error on idle client', err)
})
```

---

#### P1-2 连接池缓存竞态

**出现在原因：** getDbClient 先查 Map 再 new Pool，两个并发请求同时 miss 就会 new 两个 Pool。side project 并发低没暴露，但修起来也不复杂。

**修复方法：** 缓存 Promise 而不是 Pool 实例。getDbClient 里：
```ts
const poolPromiseCache = new Map<string, Promise<Pool>>()
if (cache.has(projectId)) return cache.get(projectId)!
const p = createPool(projectId).catch((e) => { cache.delete(projectId); throw e })
cache.set(projectId, p)
return p
```
失败时移除缓存让下次重试。

---

#### P1-3 零测试

**出现在原因：** 阶段二一直卡在 where 查询的 42P18 bug 上，修完就到时间写验收文档了，没来得及补单测。评审说得对：纯函数（buildWhereSql / parseQuery / validateData）最该测，P0-1 的 ::text bug 就是因为没单测才藏住的。

**修复方法：** 先给这三个纯函数补 vitest 单测，半天工作量。覆盖：where 等值/like/区间、sort asc/desc、必填/类型/select 选项校验、注入防护（未注册字段）。顺便把 ::text bug 锁死防回归。

---

#### P1-4 audit 日志泄露敏感信息

**出现在原因：** project.create 的 after 直接传了整行 project（含 dbConfig 明文密码）；data 路由的 after/before 传了整行业务数据，没感知 fieldType=password 的列。当时只关注"审计日志要打 stdout"，没考虑脱敏。

**修复方法：**
- audit 序列化时对 dbConfig.password 做 mask（`***`）
- data 路由的 audit 前，按 ctx.fields 把 fieldType=password 的列值替换成 `***`
- 可以在 audit.ts 里加一个 sanitize 函数统一处理

### 11.2 坚持的几点

**（1）"::text 是为了保险留的"——这个习惯本身要改。**

开发者的解释链条：42P18 → 试了各种方案 → 发现根因是 SELECT 漏拼 WHERE → 修了 WHERE → 为保险留了 ::text。

问题在于：修完根因（补 WHERE）之后，::text 就不是"修 bug 的方案"了，它变成了一个**没有注释、没有 TODO、静默改变语义的防御性代码**。三个月后没人记得它为什么在那，也没人敢删。

**要求：** 这次修 fieldType-based cast 的时候，把 `buildWhereSql` 里现在那段 `::text` 整段删掉，不是按 fieldType 分支保留。同时在 commit message 里写清楚"为何之前有 ::text、为何现在删"——否则下一次遇到 PG 类型推断问题的人（可能就是开发者自己）还会再叠一层 workaround。

**（2）P0-2 不是"阶段二范围没覆盖"，是阶段一的元数据建了空列。**

开发者说 defaultValue / isReadonly / uuidStrategy 不在阶段二的 6 个共识点里。这是事实，但反过来想：**阶段一建模时把这三列建进了 fields 表，意思就是承诺它们会生效**。现在它们是三列 dead schema——API 能写能读，但运行时不产生任何行为。

这不是阶段二漏做，是阶段一和阶段二之间的范围衔接断了。

**规则建议：** 下次分阶段时加一条——**元数据 schema 里新增一列，必须明确标注"本阶段生效 / 预留"**，否则就别建。

**（3）fieldType DB 层 CHECK 约束——优先级低同意，但理由要讲对。**

开发者说"API 层 zod 已经拦了"。这不是 DB CHECK 的价值——DB CHECK 从来不是用来挡 API 的（zod 已经挡了），它的价值是：**阶段三 DDL 引擎在生成 ALTER TABLE 时，不需要防御性处理"元数据里有个未知 fieldType"的情况**。

现在阶段二手动建测试表没事，阶段三代码生成 DDL 时，遇到一个直连 DB 塞进去的奇怪 fieldType，DDL 引擎会直接崩。

**结论：** 这条不是"低优先级"，是"阶段三开工前必须补"——不是为了挡用户，是为了挡未来的自己。

### 11.3 元观察：保留"出现在原因"的习惯

开发者回应里每个问题都写了"出现在原因"，这比单纯的"认可，会修"有价值得多——它记录了为什么会写出这段代码，下次类似问题能快速定位。


这种 message 三个月后回头看，能立刻明白决策链路。
