## 问题 1：建表时机

规划里写了两种方案：
- A. 字段都加完后，用户手动触发一个"建表"接口
- B. 第一个字段创建时自动建空表，后续加字段自动 ALTER TABLE

**倾向 B**——不用用户记着手动点"建表"，第一个字段进来就自动建表。

## 问题 2：平台默认字段 `_ctime` / `_mtime`

这两个字段是平台自动注入的（创建时间、修改时间）。要不要在 fields 元数据里也注册？

- 注册了：fields 列表里能看到，validator 知道它们，用户能在元数据里改配置
- 不注册：SELECT * 会返回这两个字段，但元数据里没有，data 路由的 loadContext 会困惑

**倾向注册**——元数据和物理表完全一致，不搞两套。

## 问题 4：删字段时物理表也 DROP COLUMN 吗

阶段一定了 fields 硬删。那删字段时的行为是：
- A. 元数据删 + 物理表 DROP COLUMN（真删列，数据丢）
- B. 元数据删 + 物理表不动（挂载自有 DB 场景，skipPhysicalDdl=true）

**倾向 A 为默认**（skipPhysicalDdl=false 时），B 为开关开启时。

## 问题 5：改字段类型怎么做 dry-run

规划说"做 dry-run 先检查能不能转"。具体方案：
- A. 事务里尝试 ALTER，失败回滚，报错给用户
- B. 先查现有列类型，对比新类型，预判能不能转

**倾向 A**——简单直接，PG 自己会检查能不能转，不用自己写类型转换矩阵。

## 问题 6：DDL 执行失败时元数据回滚

比如：先在元数据里 create 了 field 记录，然后执行 ALTER TABLE ADD COLUMN 失败了。这时候元数据里那条 field 记录怎么办？
- A. 元数据回滚（删掉刚创建的 field），保持一致
- B. 元数据保留，物理表不动，标记状态不一致

**倾向 A**——保持元数据和物理表一致，不引入"状态不一致"这种复杂状态。

## 补充问题（2026-10-26）

### 问题 7：DDL 执行顺序

选了"DDL 失败时元数据回滚"，但更简单的做法是反过来：**先执行 DDL，成功后再写元数据**。这样 DDL 失败了元数据根本没写，不需要回滚逻辑。

顺序：
- 加字段：先 `ALTER TABLE ADD COLUMN` → 成功后再 `prisma.field.create()`
- 删字段：先 `ALTER TABLE DROP COLUMN` → 成功后再 `prisma.field.delete()`

这样就不存在"元数据写了一半物理表没建"的中间状态。

---

### 问题 8：`_ctime` / `_mtime` 怎么维护

注册了这两个字段后，它们的值谁来填？
- A. PG 自动维护：`_ctime TIMESTAMP DEFAULT NOW()`，`_mtime TIMESTAMP DEFAULT NOW()`，加 trigger 在 UPDATE 时自动更新
- B. 应用层维护：create 时 INSERT 里带上 `NOW()`，update 时 SET `_mtime=NOW()`

倾向 A——PG trigger 自动维护，应用层不用管。

### 问题 9：第一个字段不是主键时怎么建表

第一个字段创建时自动建表，但如果那个字段不是主键，建出来的表就没有 PRIMARY KEY。后续加主键字段时再 ALTER TABLE ADD PRIMARY KEY？

还是说：等主键字段加进来才建表，之前的字段先攒着？

倾向：第一个字段进来就建表（可能没主键），后续加主键字段时 ALTER TABLE ADD PRIMARY KEY。简单直接。

---

### 问题 10：删主键字段时怎么处理

PG 不允许直接 DROP 主键列（会报错）。删主键字段时要先 `ALTER TABLE DROP CONSTRAINT` 再 `DROP COLUMN`。这个 DDL 引擎要处理吗？

还是说：删主键字段时拒绝，提示"先删表重建"？

倾向：处理——先 DROP CONSTRAINT 再 DROP COLUMN，一步到位。
