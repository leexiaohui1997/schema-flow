### 问题2：适配器接口长什么样？

要抽象一个统一的 DB 适配器接口。方法签名怎么定？

**方案A：直接传 SQL**
```ts
interface DbAdapter {
  // DDL
  createTable(sql: string): Promise<void>
  alterTable(sql: string): Promise<void>
  
  // DML
  query(sql: string, params: unknown[]): Promise<unknown[]>
  insert(sql: string, params: unknown[]): Promise<unknown>
  update(sql: string, params: unknown[]): Promise<number>
  delete(sql: string, params: unknown[]): Promise<number>
  
  // 连接池管理
  end(): Promise<void>
}
```

**方案B：细粒度方法**
```ts
interface DbAdapter {
  createTable(columnDefs: ColumnDef[]): Promise<void>
  addColumn(table: string, column: ColumnDef): Promise<void>
  // ...
}
```

**规划方倾向方案A**——DDL 生成器已经生成好了 SQL，适配器只负责执行。这样适配器接口简单，DDL 生成器可以按 DB 类型分别写。

### 问题5：DDL 引擎怎么适配多DB？

阶段三的 `ddlGenerator.ts` 是 PG 专用的。MySQL 的类型映射不一样：
- PG 的 `SERIAL` → MySQL 的 `INT AUTO_INCREMENT`
- PG 的 `JSONB` → MySQL 的 `JSON`
- PG 的 `TIMESTAMPTZ` → MySQL 的 `DATETIME`

怎么抽象？

- A. 一个 `ddlGenerator.ts`，内部按 dbType 分支
- B. 拆成 `pgDdlGenerator.ts` + `mysqlDdlGenerator.ts`，统一接口

**规划方倾向 B**——分文件更清晰，未来加更多 DB 类型不会让一个文件变成几百行的分支。

> @开发 你觉得哪种方式写起来更顺手？

---

### 问题6：查询解析器怎么适配多DB？

阶段二的 `queryParser.ts` 里有 PG 专用的语法（比如 `::text` cast）。MySQL 语法不一样：
- PG 的 `::text` → MySQL 的 `CAST(x AS CHAR)`
- PG 的 `ILIKE` → MySQL 的 `LIKE`（不区分大小写）

怎么抽象？

- A. `queryParser.ts` 里按 dbType 分支
- B. 拆成 `pgQueryParser.ts` + `mysqlQueryParser.ts`

**规划方倾向 B**——和 DDL 生成器一样，分文件更清晰。

> @评审 你觉得这个拆分粒度合适吗？会不会过度设计？

## 评审方发言（2026-10-26）

逐题表态，最后说两个 Q&A 没覆盖到的。

### Q1：dbType 加在哪？

**同意 A（dbConfig JSON 里）。** 理由：dbConfig 本来就是 JSON 字段，加 dbType 不用改表结构；未来加 ssl、pool size 等连接配置也都在 JSON 里。projects 表加独立列会让 schema 变重，而且 dbType 本质是"连接配置"不是"项目属性"。

补一条：**dbType 创建后只读**，和 tableName/fieldKey 一样。项目创建后改 dbType 等于换数据库，物理表要不要迁移？这个不该在运行时支持。

### Q2：适配器接口长什么样？

**同意方案 A（直接传 SQL）。** DDL 生成器和 queryParser 已经生成好 SQL 了，适配器只负责执行，接口粗一点没关系。

但有一个隐患要指出来：**不同 DB 的参数占位符不一样**——PG 用 `$1, $2`，MySQL 用 `?, ?`。如果适配器只收 SQL + params，SQL 里的占位符必须和 DB 匹配。这意味着占位符生成的责任在 queryParser 层（Q6 已经拆了，正好），不要让适配器去转。

### Q3：MySQL 用什么库？

**mysql2/promise，没有更好的。** 老 `mysql` 库已经不维护了，mysql2 是事实标准。不用纠结。

### Q4：LRU 缓存策略？

**同意 A（不加 LRU）。** 低代码平台项目数确实不会多，LRU 是过度设计。

但要补一个之前评审提过没修的：**项目软删/硬删时要 closeDbClient**。现在 dbConnection.ts 里的 Map 不会清，项目删了 Pool 还挂着——这才是真正的内存泄漏风险，不是 LRU 的问题。再加一个 Pool 自身的 `idleTimeoutMillis`（比如 30 分钟），闲置连接自动回收。这样不用 LRU 也能防泄漏。

### Q5：DDL 引擎怎么适配多DB？

**同意 B（拆 pgDdlGenerator + mysqlDdlGenerator）。** 但要补一条：两个生成器实现同一个 `DdlGenerator` interface，上层 fields.ts 按 dbType 选实例，不要在路由里写 `if (dbType === 'mysql')`。

### Q6：queryParser 怎么适配多DB？

**同意 B（拆 pgQueryParser + mysqlQueryParser）。** 拆分粒度合适，不过度设计。queryParser 本来就有 DB 专用语法（::text、ILIKE、占位符），硬塞一个文件会变成 if-else 地狱。

提醒三点：
- 阶段二修过的 `::text` cast bug，MySQL 里对应 `CAST(x AS CHAR)`
- 占位符 `$1` vs `?` 在 queryParser 层处理
- MySQL 的 LIKE 默认不区分大小写，PG 的 ILIKE 语义直接映射

### Q7：validator 怎么适配多DB？

**同意不用改。** validator 是纯 JS 字段校验（必填、长度、正则、类型），和 DB 无关。确认一下：validator 里的 type 校验（number/boolean/date）都是 JS 层判断，不发 SQL，对吧？

### Q8：挂载用户自有DB模式——和多DB适配是什么关系？

**这两个不是同一个东西，但共享同一套适配器接口。**

- **多DB适配** = SchemaFlow 自己的业务库可以是 PG 或 MySQL（dbType 决定用哪个 Pool）
- **挂载用户自有DB** = SchemaFlow 连接用户的数据库，对用户的表做 CRUD 代理（skipPhysicalDdl=true，不建表）

关键判断：**阶段四只做多DB适配，"挂载自有DB"排到后面。** 理由：
1. 多DB适配是内部技术债（让 SchemaFlow 能选 MySQL），范围清晰
2. 挂载自有DB是产品功能（用户配外部连接串、权限、安全、连接串加密），涉及面广
3. 阶段三已经做了 skipPhysicalDdl 开关，挂载自有DB只是在那个开关上再加一层"用户配外部连接"——等多DB适配器稳定了再做不迟

### Q&A 没覆盖到的两条

**1. dbType 创建后只读。** 已经在 Q1 说了，不重复。

**2. healthz 要探两种 DB。** 阶段四做完 MySQL 后，healthz 不能只探 PG。这个排到阶段四收尾。

### 结论

8 个问题全部有明确方向，没有阻塞项。阶段四可以开工。开工前记着：
- dbType 加在 dbConfig JSON 里，创建后只读
- 适配器接口收 SQL + params，占位符在 queryParser 层生成
- 不加 LRU，但要补 closeDbClient + idleTimeoutMillis
- DDL 生成器和 queryParser 都按 DB 类型拆文件，实现统一 interface
- 阶段四不做"挂载自有DB"，只做多DB适配
